# TASKS.md - работа над фичами

Открывается на каждую слайс-сессию поверх `tech.md`. Одна задача этого файла = один вертикальный слайс = одна ветка = один PR.

---

## Прочитай первым

1. Подчиняйся `tech.md` дословно: типы, схема БД, роуты, статус-машина, конвенции кода и коммитов - из него, не изобретаются заново.
2. Контракт не выдумывается. Если задачи не хватает контракта - см. блок ниже.
3. Слайс повторяет структуру эталонной вертикали (см. «Эталон» ниже), не изобретает раскладку заново.
4. Задача = одна строка из списка ниже = один PR. Не смешивать бэкенд и фронтенд одной задачи, если явно не указано «backend+frontend» - это два отдельных PR.

## CONTRACT GAP

Не хватает контракта, типа, поля или роута - сессия останавливается и выдаёт:

```
CONTRACT GAP
Нужно: <что>
Зачем: <какая задача блокируется>
Предлагаемая форма: <точное определение поля/типа/роута>
```

Код с выдуманным типом не пишется. Дальше - либо продолжить слайс на локальной заглушке с явной пометкой `// TODO(contract-gap): ...`, либо остановиться, если заглушка невозможна без искажения бизнес-логики. Пробел решается отдельной архитектурной сессией: контракт аппендится в `tech.md`, версия бампается.

## Эталон

Все слайсы сверяются со структурой эталонной вертикали из `SKELETON.md` (раздел 3, пункт 11): главная → добавление в корзину → HTML-фрагмент корзины, с тестами. Домен → репозиторий → хендлер → шаблон → тест, в этом порядке, без пропуска слоёв.

## Стадийный список задач

Каждая карточка: цель, что трогает, какие компоненты и типы из `tech.md` использует, критерии приёмки, тесты по доктрине §11 `tech.md`.

### S1. Каталог

**S1.1 - Главная с тремя карточками и hover-флипом**
- Домен/роут: `GET /` (§5.2), `domain/catalog` только на чтение.
- Типы/компоненты: `catalog.Product`, `catalog.Variant` (§6.3), компонент `Card` (§7.2).
- Приёмка: три активных товара отрисованы в порядке `sort_order`; наведение меняет `image_front` → `image_back` без JS (Tailwind `group-hover`); на touch-устройстве тап по бейджу `flip` переключает вид (Alpine).
- Тесты: `httptest` на рендер главной с сид-данными; property-тест не нужен (чистая вёрстка).

**S1.2 - Страница товара, выбор размера, sold out**
- Домен/роут: `GET /product/{slug}` (§5.2).
- Типы/компоненты: `catalog.Variant.Available()` (§6.3), `Badge`, `Select`.
- Приёмка: размер с `Available() == 0` неактивен и помечен `sold out`; несуществующий `slug` → 404 через общий error-хендлер.
- Тесты: `httptest` на 200/404; таблица размеров с `Available()==0` и `>0`.

### S2. Корзина

**S2.1 - Добавление/изменение/удаление позиции**
- Домен/роут: `POST /cart/items`, `PATCH /cart/items/{id}`, `DELETE /cart/items/{id}` (§5.2), `domain/cart`.
- Типы: `cart.Cart`, `cart.CartItem`, ошибка `ErrCartItemLimit` (§6.5).
- Приёмка: `qty` вне `1..10` → 422 с текстом ошибки; ответ - HTML-фрагмент корзины (HTMX-паттерн §5.3), не полная страница; `cart_id` в подписанной cookie, создаётся при первом добавлении.
- Тесты: идемпотентность повторного `PATCH` с тем же `qty`; путь ошибки на `qty=0` и `qty=11`.

**S2.2 - Страница корзины и расчёт сумм**
- Домен/роут: `GET /cart` (§5.2).
- Типы: `money.Amount.Add` (§6.1).
- Приёмка: сумма позиций равна сумме корзины при любом наборе строк; доставка из `settings.shipping_cents`.
- Тесты: property-based на инвариант «сумма корзины = сумма позиций» для случайных наборов qty/price.

### S3. Заказ и оплата

**S3.1 - Чекаут: валидация, создание заказа, снимок цены, резерв стока**
- Домен/роут: `GET /checkout`, `POST /checkout` (§5.2), `domain/order`.
- Типы: `order.Status` (§6.2), `Touch` (§6.4) из cookie `ft`/`visits`.
- Приёмка: `reserved += qty` в транзакции с проверкой `stock - reserved >= qty`, иначе `ErrOutOfStock`; `order_items` хранит снимок цены, не ссылку; `expires_at = now() + 30m` (§15 `tech.md`, решения по умолчанию); валидация длины `customer_name`/`comment` в рунах (§16.1 `tech.md`).
- Тесты: инвариант стока при параллельных резервах; путь ошибки при `stock - reserved < qty`.

**S3.2 - Интеграция NOWPayments за интерфейсом + фейк**
- Домен/роут: `internal/payments/nowpayments`, вызывается из хендлера `POST /checkout`.
- Типы: интерфейс `payments.Client` (§5.4 `tech.md`).
- Приёмка: реальный клиент создаёт инвойс с таймаутом 5с (§16.2 `tech.md`); редирект 303 на `invoice_url`; фейк отдаёт детерминированный `invoice_url` для тестов и дев-режима.
- Тесты: контрактный тест фейка против зафиксированного в `tech.md` payload; путь ошибки на 500/таймаут провайдера.

**S3.3 - IPN-эндпоинт: подпись, дедуп, статус-машина, списание стока**
- Домен/роут: `POST /webhook/nowpayments` (webhook-группа §5.2).
- Типы: `order.CanTransition` (§6.2), `ErrInvalidSignature` (§6.5).
- Приёмка: подпись (`hmac.Equal`, SHA-512) проверяется до разбора тела; `dedup_key` гарантирует один переход на один платёж; при `paid`: `stock -= qty, reserved -= qty` одной транзакцией.
- Тесты: идемпотентность на дублирующийся и переставленный по порядку IPN (§11 `tech.md`, пункт 2); путь ошибки на битую подпись и `partially_paid`.

**S3.4 - Страница `/order/{token}` с поллингом и таймером резерва**
- Домен/роут: `GET /order/{token}` (§5.2).
- Типы/компоненты: `StatusPill`, `Money` (§7.2).
- Приёмка: поллинг раз в 10с (Alpine); таймер обратного отсчёта до `expires_at`; несуществующий/просроченный токен → нейтральная страница без утечки существования заказа.
- Тесты: `httptest` на валидный/невалидный `public_token`.

**S3.5 - Воркер освобождения просроченных резервов**
- Домен: `internal/worker`.
- Приёмка: раз в минуту находит заказы `status=awaiting_payment AND expires_at < now()`, переводит в `expired`, снимает `reserved`.
- Тесты: инвариант `stock - reserved >= 0` после прогона воркера на случайных данных; идемпотентность повторного запуска на уже обработанных заказах.

### S4. Telegram-статусы

**S4.1 - `tg_link_code`, кнопка и QR «Track in Telegram»**
- Домен/роут: расширение `GET /order/{token}` (§5.2).
- Приёмка: код генерируется `crypto/rand`, 16 hex (§5.1 `tech.md`, раздел «Токены»); QR ведёт на `t.me/<bot>?start=<code>`.
- Тесты: уникальность кода на 10k генераций (табличный/property-тест).

**S4.2 - Webhook бота: дедуп `update_id`, `/start <code>`, привязка, `/status`**
- Домен/роут: `POST /webhook/telegram` (§5.5 `tech.md`).
- Типы: `telegram.Bot` интерфейс (§5.5 `tech.md`).
- Приёмка: несовпадение secret-token → 401; повторный `update_id` → 200 без побочных эффектов; код не найден → нейтральный ответ.
- Тесты: идемпотентность на дублирующийся `update_id`; путь ошибки на неизвестный код.

**S4.3 - Outbox-уведомления на каждый переход статуса**
- Домен: `internal/worker`, таблица `notifications`.
- Приёмка: `dedup_key` = `order_id|kind|status`, одно сообщение на переход; ретраи с бэкоффом 30с/2м/10м/1ч/6ч, максимум 5 попыток.
- Тесты: идемпотентность повторной обработки одной и той же `pending`-записи; путь ошибки на фейке, возвращающем 429.

### S5. Админка (web)

**S5.1 - Аутентификация, сессии, rate limit, layout админки**
- Домен/роут: `POST /admin/login`, middleware `adminauth` (§8.5 `tech.md`).
- Приёмка: argon2id, сессия в БД 12ч, rate limit 5/15мин/IP (§9 `tech.md`).
- Тесты: путь ошибки на превышение лимита попыток.

**S5.2 - Заказы: список, фильтры, карточка, ручные переходы статуса**
- Домен/роут: `GET /admin/orders`, `GET /admin/orders/{id}`, `POST /admin/orders/{id}/status` (§5.2 `tech.md`).
- Типы/компоненты: `order.CanTransition` (§6.2), `Table`, `StatusPill`, `Pagination`.
- Приёмка: ручной переход `paid → shipped → delivered` или `→ cancelled` ставит уведомление в outbox; откат назад запрещён на уровне `CanTransition`.
- Тесты: путь ошибки на попытку недопустимого перехода.

**S5.3 - Товары: правка цены с `price_history`, правка стока**
- Домен/роут: `POST /admin/products/{id}/price` (§5.2 `tech.md`).
- Приёмка: `reason` обязателен; запись в `price_history`; изменение цены не влияет на уже созданные заказы (снимок в `order_items`).
- Тесты: инвариант - цена в существующих `order_items` не меняется после правки цены товара.

**S5.4 - Настройки (доставка, TTL, пауза магазина)**
- Домен/роут: `GET/POST /admin/settings` (§5.2 `tech.md`), таблица `settings`.
- Приёмка: значения читаются/пишутся через единый key-value репозиторий, не через отдельные колонки конфига.
- Тесты: round-trip записи и чтения по каждому известному ключу.

### S6. Аналитика

**S6.1 - Middleware атрибуции, `visits`, `events`, отсечение ботов**
- Домен: `attribution` middleware (§5.6 `tech.md`).
- Приёмка: cookie `vid` (365д), `sid` (30мин скользящее окно); известные боты по User-Agent помечаются `is_bot=true` и исключаются из метрик.
- Тесты: новый `sid` создаёт запись в `visits` с корректными UTM-полями из query.

**S6.2 - SQL-агрегаты и `GET /admin/api/metrics`**
- Домен/роут: `GET /admin/api/metrics?range=&granularity=` (§8.2 `tech.md`).
- Приёмка: агрегаты считаются SQL-запросами, не Go-циклом по строкам (§8.2 `tech.md`).
- Тесты: контрактный тест формы JSON-ответа под каждый `granularity`.

**S6.3 - Дашборд: StatCards, выручка/заказы с маркерами смены цены**
- Компоненты: `StatCard`, `ChartCanvas` (§7.2 `tech.md`).
- Приёмка: маркеры на графике берутся из `price_history` за выбранный период.
- Тесты: `httptest` на рендер дашборда с сид-данными.

**S6.4 - Воронка и источники трафика**
- Домен/роут: расширение `GET /admin/api/metrics`.
- Приёмка: воронка визиты → просмотр товара → добавление в корзину → чекаут → оплата, с процентами перехода; таблица по `utm_source/medium/campaign` и `referrer` с выручкой и конверсией.
- Тесты: воронка на сид-данных даёт монотонно убывающие числа по этапам.

### S7. TG Mini App админка

**S7.1 - Валидация `initData`, allowlist, короткая сессия, `/tgapp`**
- Домен/роут: `GET /tgapp` (§5.2 `tech.md`), валидация по алгоритму §5.5 `tech.md`.
- Приёмка: `auth_date` не старше 15 минут; `user.id` обязан быть в `admin_users.telegram_id`; промах → 403 без деталей.
- Тесты: путь ошибки на просроченный `auth_date` и на `user.id` вне allowlist.

**S7.2 - Layout AdminMini поверх тех же хендлеров**
- Приёмка: те же хендлеры `admin/*`, отдельный layout, без логин-формы, цвета из `themeParams` Telegram.
- Тесты: `httptest` на рендер `/tgapp/orders` с валидной сессией.

**S7.3 - Адаптация графиков и таблиц под узкий экран**
- Приёмка: `ChartCanvas` и `Table` рендерятся без горизонтального скролла на ширине Mini App (~360-420px).
- Тесты: не автоматизируется (вёрстка), проверяется вручную в Telegram-клиенте.

### S8. Продакшн

**S8.1 - HTTPS и Caddy, домен, реальные ключи**
- Приёмка: `docker/compose.yml` и `Caddyfile` из `SKELETON.md`; реальные `NOWPAYMENTS_API_KEY`, `TELEGRAM_BOT_TOKEN`; `setWebhook` выполнен на реальный домен.
- Тесты: не unit, проверяется в раскатке (S8.3).

**S8.2 - Бэкапы БД по расписанию, ротация логов, `/healthz`**
- Приёмка: `/healthz` отдаёт 200 при живом соединении с Postgres; бэкап - cron-задача на VPS, не в приложении.
- Тесты: `httptest` на `/healthz` с оборванным пулом соединений → 503.

**S8.3 - Полный сценарий на реальном платеже минимальной суммы**
- Приёмка: главная → добавление в корзину → чекаут → реальный крипто-платёж → IPN → `paid` → уведомление в Telegram, на живом домене.
- Тесты: ручной прогон, фиксируется в PR-описании, не автоматизируется.

## Рабочий цикл задачи

1. Ветка `feat/<slice-name>` или `fix/<slice-name>` из задачи в списке выше.
2. Коммиты по ходу работы, маленькие, по конвенции §12 `tech.md` (английский, Conventional Commits, без следов нейросети, автор `AZAZ3LL0 <sadrievsamat4@gmail.com>`).
3. Самопроверка перед мёрджем (чек-лист ниже) - проходишь сам, либо отдаёшь диф отдельной свежей сессии как второе мнение.
4. Мёрдж в `main` только через PR с зелёным CI-гейтом.
5. Автодеплой по мёрджу (см. `SKELETON.md`, раздел 1).

## Самопроверка перед мёрджем

- нет типов и полей вне `tech.md`;
- обработчики внешних событий идемпотентны и покрыты тестом на повтор;
- подписи проверяются до разбора тела;
- UI собран из компонентов §7.2 `tech.md`, разметка не продублирована;
- деньги нигде не стали `float`;
- запросы к БД параметризованы и лежат в репозитории домена;
- контекст и таймаут есть у каждого внешнего вызова;
- не тронуты чужие домены и общие файлы без явного намерения (см. «Защита общих файлов» в `SKELETON.md`);
- тесты проверяют контракт из задачи, а не повторяют реализацию;
- в сообщениях коммитов нет следов нейросети, автор - `AZAZ3LL0`.

## Что НЕ трогать внутри фичевой сессии

- Чужие и будущие домены (например, слайс S3 не трогает `internal/telegram`).
- Общие файлы: UI-примитивы, layout, схема БД, общие типы (§6 `tech.md`) - правка только отдельной архитектурной сессией с бампом версии `tech.md`.
- Миграции - не пишутся мимоходом внутри фичевой задачи; новая миграция - отдельный коммит с явным намерением, отражающий бамп версии `tech.md`, если схема меняется.
- Сквозные правки (например, смена конвенции именования роутов) - отдельная архитектурная сессия, не попутно с фичей.
